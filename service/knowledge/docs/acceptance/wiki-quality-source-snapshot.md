`ReadWikiQualitySourceSnapshot` 必须显式传入 `module_id,page_id,fact_set_revision_id,wiki_revision_id,source_scope_revision`。它在一个 PostgreSQL `REPEATABLE READ READ ONLY` 事务中按历史 FactSetRevisionID 回查固定 Catalog 及原 FactSet Event，再逐个检查该 Catalog 的完整 SourceRevisionID/SHA、Source 当前撤回位、目标 Wiki 当前撤回位；对每个 `required=true` 的 Fact 读取同目标 `(wiki_revision_id,fact_id)` 当前判断 head、判断修订原 EventID/JSON/raw SHA/JCS SHA，并核 FactID、Wiki 内容 SHA、Source 版本/SHA、locator、引文和原字节 span 与 Catalog 一致。缺判断 head 保留空项并将 `AllRequiredHaveHead=false`；损坏或缺失的 head/Event sidecar、同名 Fact 错绑、Source 资格对象损坏则拒绝，不把技术事件数当判断覆盖。

这份结果只证明**RTW 在该事务数据库快照读时**的 head 与 Source/Wiki 撤回状态。`WikiAndSourcesAvailableAtRead=true` 不检查真人是否漏列事实、不验证管理员是否经 UserCenter 实时授权，也不证明 D07 页面质量。`actor_id` 仍是 Admin JWT 加 `AdministratorIDs` 白名单的原 `userId` 字面值，允许 `test-admin`；不能把它改写成 UserCenter UID，更不需要当前产品不存在的租户字段。历史 Catalog 和历史质量原 Event 在后续 Source 撤回后仍可原样回查，资格必须单独按需要的时点判断。

当前 DataCenter ACK cutoff **不能**由这份读时快照回推。RTW 的模块 `event_sequence` 给原 Event `aggregate_version` 排序，但当前 Outbox Dispatch 的送达顺序可能跨类型或并发地不同于该版本顺序，`delivered_at`/最大已送版本亦不足以签连续水位。未来若要签 `as_of_dc_offset=C`，需在同一模块上可验：RTW 源 Outbox 到版本 `V` 的连续已送事件清单及 EventID→DC 实际 offset 映射；DC 从 1 到 `C` 的完整 producer 前缀含所有 `<=V` 所需的目录、判断、Source/Wiki 撤回事件且无版本缺口；截止版本内用 `base_fact_set_revision_id`、`base_judge_revision_id` 前驱链重建目标修订的最后判定和 Source 资格。任一缺口、重排未证明或相关事件未 ACK 都必须继续 `not_evaluable`，不能套用现时 head。这里仅记录待实现交接合同，没有生成 as-of 收据。
